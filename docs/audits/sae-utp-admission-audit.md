# SAE 与 UTP 平台能力准入审计

> 状态：未准入。本文只定义能力分类和进入 Marketplace 的证据门槛，不代表 `oec-sae`、`oec-utp`
> 或 `oec-testing` 已实现。当前仓库不创建这些 Plugin 目录，也没有对应 Marketplace entry。

## 1. 审计原则

平台能力是否迁移，不以旧 payload 中存在多少脚本或 `SKILL.md` 为依据，而看它是否具备稳定用户目标、
类型化接口、可验证远端身份和受控副作用边界。

准入前必须明确：

- 真实 API 契约、成功码和错误语义。
- 固定可信 origin、认证方式、权限范围和脱敏规则。
- 可用于验收的非生产环境和明确远端对象身份。
- workspace、配置和远端对象的绑定方式。
- 写操作的 prepare、确认、execute、status 或等价硬门禁。
- 幂等键、未知写结果的查询恢复和 partial checkpoint。
- 不接受任意 payload、任意命令、任意状态码或任意字段更新。
- mock/integration 与真实外部验收分别记录。

任何一项缺失，都不能用 Prompt、Bash 路由或“取第一个候选”补偿。

## 2. SAE 能力分类

旧 SAE 资产覆盖约 21 类操作，应按所有权和风险拆分，而不是整体搬迁。

### 2.1 首轮只读候选

- 查询应用及其明确环境的状态。
- 查询版本、实例和发布结果。
- 按受限时间窗和应用身份查询日志。
- 验证一次已知部署对应的运行健康。

这些能力仍需先验证真实 API、字段归一化、分页、权限和稳定的应用/环境身份。日志接口必须限制时间窗、
结果量和敏感信息，不开放任意日志后端查询语言。

### 2.2 后续受控写入候选

只有当真实部署入口、非生产环境标识和状态回读均已验证后，才评估受控部署链：

```text
prepare deployment
→ 精确选择应用和环境
→ 展示版本、配置和影响范围
→ 用户确认
→ execute deployment
→ status 验证
```

它不能接收任意 Kubernetes manifest、Helm values、shell command 或平台原始 payload。

### 2.3 默认排除

- 任意 `kubectl`、Helm 或集群命令。
- namespace、成员、角色、配额和密钥 CRUD。
- 应用、环境、实例和基础设施的通用管理接口。
- 生产环境的自动推断或默认选择。
- 无明确远端身份的批量操作。

上述能力不是因为模型做不到而排除，而是它们扩大了权限面，且不属于“验证或受控发布一个已知变更”
这一稳定原子目标。

## 3. UTP 与旧测试资产分类

旧测试体系约有 71 个嵌套 Skills。嵌套文件数量不等于 71 个值得平台化的原子能力，必须逐项记录：

| 维度 | 审计问题 |
| --- | --- |
| 使用频率 | 是否有持续、可观察的团队场景 |
| 能力性质 | 工程方法、确定性本地脚本，还是远端平台 API |
| 输入输出 | 是否能定义小而稳定的 schema 与结果语义 |
| 外部依赖 | 是否需要 UTP、设备、账号、数据或专有环境 |
| 副作用 | 是否创建、执行、修改或删除远端对象 |
| 身份与幂等 | 是否有稳定 case/run ID 和未知结果恢复方式 |
| 维护归属 | 由工程规范、测试团队还是平台团队负责 |
| 验收证据 | 静态、mock、集成、非生产真实运行分别有哪些 |

处置规则：

- 通用测试方法只在高频且模型无法稳定自行判断时成为聚焦 Skill，不恢复 Dispatcher。
- 纯本地、确定性的解析和校验成为可执行工具，并继承仓库现有测试框架。
- UTP 的用例、计划、执行和报告进入 MCP 前，必须有真实 API 与稳定身份契约。
- 只有独立上下文、并行或权限隔离通过 eval 证明收益时才创建测试 Agent。
- 不再通过一个顶层 Skill 按路径读取几十个内部 `SKILL.md`。

## 4. 准入和发布门禁

一个新平台 Plugin 进入 Marketplace 前至少需要：

1. 固定版本的 API/客户端证据和字段契约。
2. 非生产目标、账号权限和可恢复的认证流程。
3. roots 约束、workspace 绑定和精确远端候选选择。
4. 写操作的不可变 plan token、宿主确认元数据和服务端复查。
5. ID、标题、父子或环境关系的远端 read-back 验证。
6. 无盲重试、无任意 payload、无 prod/unknown fallback。
7. 自足 bundle、无 `node_modules` 安装验收和工具数量验证。
8. mocked failure/partial/ambiguity 覆盖以及一次明确授权的真实非生产旅程。
9. 文档清楚区分已实现、自动验证和真实 E2E。

通过审计后也应按平台生命周期分别制定 `oec-sae` 或 `oec-utp` 计划，不创建混合的 delivery Plugin。

## 5. 当前结论

- SAE：只读诊断候选方向清晰，但真实 API、认证、权限、日志边界和非生产身份尚未完成验证，未准入。
- UTP：旧资产仍需逐项清点和归属分类，不能从嵌套文件树直接推导 Plugin 结构，未准入。
- Marketplace：保持 Product、Engineering、E3 和 Pipeline 四个 Plugin；SAE/UTP 组件数为零。
- 真实操作：本轮不执行 SAE、UTP 或部署写入。
